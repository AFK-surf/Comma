# 搜索读取行数：优化验证

2026-09-06。staging 只读诊断；物理布局对照在独立本地 ClickHouse 中完成。

**可以显著减少读取行数，有效方向是缩小物理读取粒度，并在独立检索层收敛回源范围。单改 CTE 未产生收益。** 本轮交付是诊断、可复跑实验和落地约束，尚未修改线上表或正式搜索实现。

## staging 的成本来源

对近期繁忙频道的同一 60 天范围、同一查询向量，完整 SQL 读取 **83,575 行、180,503,807 B**，返回 20 个候选。为观测完整成本，这一轮诊断临时允许最多 200,000 行；这不是修改应用的 65,536 行预算，也不是一次应用预算通过结果。

拆分观察结果：

| 部分 | 逻辑记录 | 数据库读取行数 | 读取字节 |
| --- | ---: | ---: | ---: |
| 消息与 payload 合并、当前正文/附件引用读取 | 12,906 条消息 | 57,545 | 112,228,164 |
| 文本与附件索引扫描 | 8,305 条索引记录 | 26,218 | 67,130,890 |

约 69% 的读取行数出现在原文状态读取部分。记录数、单元数与物理读取行数不同；一条索引记录也可能包含多个向量。拆分与完整查询发生在不同时间，后台写入和合并仍在继续，因此不把两次观测之和当成同一个一致快照。

## 已排除的 SQL 改写

| SQL 变体 | 读取行数 | 结果与原 SQL 一致 |
| --- | ---: | --- |
| 原 SQL | 83,575 | 基准 |
| 物化原文状态 CTE | 83,576 | 是 |
| 物化索引内容 CTE | 83,576 | 是 |
| 两个 CTE 都物化 | 83,576 | 是 |
| 物化后用已有索引消息键过滤原文状态 | 108,164 | 是 |

物化语法和设置依据 [ClickHouse 26.3 官方发布说明](https://clickhouse.com/blog/clickhouse-release-26-03)。上述实验没有发现值得保留的读取量收益；不会因为某次耗时略短就引入额外临时结果和设置。只按已有索引消息键筛选仍命中了相同的数据块，还增加了中间读取。

## 有效对照：读取粒度

本地 ClickHouse 26.4.5.143，2 核 / 4 GiB。三套独立数据库使用相同 SQL、相同 120,000 条合成文字消息、40 个频道、66,047 条文本索引记录和 60 天查询窗口；附件索引为空。保持 `index_granularity_bytes=10 MiB`，只改变创建表时的 `index_granularity`。该参数是每个 granule 的行数上界，实际粒度也受字节阈值影响。

分别验证引擎自动选择的 Wide/Compact 布局和强制 Compact 布局。所有变体的 20 条完整结果均与基准相同。

### 与 staging 相同的 Compact 类型

| 创建表时的行粒度上界 | 实际读取行数 | 读取字节 | 65,536 行应用预算 |
| ---: | ---: | ---: | --- |
| 8,192 | 69,308 | 122,902,306 | 失败，Code 158 |
| 2,048 | 26,624 | 45,092,422 | 通过 |
| 1,024 | 15,360 | 26,699,204 | 通过 |

1,024 对照比 8,192 对照少读 **77.8% 的行和 78.3% 的字节**。应用预算没有提高，查询由失败变为成功。在这份合成数据中，磁盘占用增加约 1.8%；该比例不能推广到其他语料或写入负载。

自动选择布局的对照也由 69,308 行降到 15,360 行；读取字节由 42,245,692 B 降到 21,582,752 B，说明布局类型会影响字节收益。单次延迟保存在原始数据中，不将本地单样本计时视为线上 P95。

这个实验隔离的是读取粒度，没有验证真实多模态向量质量、写入吞吐或大规模合并成本，也不是已经把 staging 的 83,575 行降低到 15,360 行。

## 落地约束与建议

本地实测，ClickHouse 26.4 的 `ALTER TABLE ... MODIFY SETTING index_granularity` 和 `index_granularity_bytes` 都返回 `READONLY_SETTING`。因此不能靠在线改一个设置就让现有数据获得这些收益。

按既定[独立消息检索层目标](../../../../docs/salix/message-search-target.md)推进：

1. 后续用户已选择 2,048 粒度，见[决定与影响范围](../../../../docs/salix/slack-semantic-read-layout.md#2048-粒度决定与影响范围)。本轮实验同时调整两张 canonical 消息表和两张派生索引表；只改派生表时不能直接沿用共同调整的收益。新表上线前仍须测量写入与合并代价。canonical 当前状态来自源行，不另建异步状态镜像；OpenSearch 的 HNSW 不使用此 ClickHouse 设置。
2. 让检索层决定有界候选，再按[发布协议](../../../../docs/salix/message-search-publication.md)验证当前来源，减少每次扫描整个时间窗口的原文。保持版本、删除、同版本内容变化和 group/connect 授权语义；不能直接删除这些检查，或用未经校验的前 20 个片段替代原来的消息结果。
3. 新表和索引构建采用在线回填与发布，保持现有服务和数据可用。不能原地停服重建，也不为这次优化向完整消息表添加检索物化列。
4. 用真实 staging 向量和完整入口验证回填后的召回、读取预算与并发，再重评 30/60/90 天边界。30 天是现有布局的观测边界，不应成为新架构的永久限制。
